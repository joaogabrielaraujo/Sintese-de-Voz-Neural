# Phase 15.1 Research Notes

Date: 2026-08-10

## Evidence from the repository

- `PipelineOrchestrator.processChapterStream` already awaits one `engine.synthesizeWithMetrics` call per sentence, so the current producer is sequential. The observed competition risk is more likely queue/prefetch lifecycle, runtime construction, or UI/audio copies than simultaneous calls in this method.
- `main.dart` currently creates `CircularAudioBuffer(maxItems: 3)` and prepares one next item. This is a useful baseline for adaptive queue work, but startup minimums and profile limits are not represented as policy objects yet.
- `SupertonicOnnxEngine` now has a persistent isolate worker in the working tree, but it requires lifecycle tests, error cleanup, serialization tests, and validation before it can be treated as production-ready.
- `RTFCalculator` already computes inference time, audio duration, and RTF. The phase should extend the metrics model instead of introducing a parallel RTF formula.
- `AudioBuffer` preserves the generated sample rate. `pipeline_result.dart` currently rejects mixed sample rates when combining audio, so any chapter-level aggregation must resample explicitly or keep chunks separate.
- Existing `CircularAudioBuffer`, `MockTTSEngine`, streaming telemetry, and pipeline tests are reusable regression fixtures.

## External technical references

- Sherpa-ONNX documents Supertonic as an offline TTS model with explicit language, speaker, speed, and diffusion-step configuration. The phase should record the effective values used in each generation.
- Sherpa-ONNX exposes model-specific generated sample rate; the application must use that returned value rather than assuming the Faber 22050 Hz rate.
- The official Android examples demonstrate local/offline operation but do not prove that embedding a roughly 145 MB extracted Supertonic package is acceptable for this APK. Asset delivery remains a measured decision.

## Planning implications

1. The first production tracer is persistent worker -> one scheduler request -> bounded queue -> existing audio player -> one metrics record.
2. Batching must be introduced after the serialized path is measured, because it changes sentence highlighting and audio duration accounting.
3. Adaptive speed is a policy layer; it must not mutate the engine's configured speed without emitting `speed_requested` and `speed_effective` metrics.
4. Cache and profile work must remain optional so Faber, mocks, and existing tests do not acquire Supertonic-specific assumptions.
5. Device validation is a human gate: Windows measurements can validate reproducibility, but only the Motorola G85 can validate UI smoothness, RAM, thermal behavior, and APK asset strategy.
